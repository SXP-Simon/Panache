# 跨平台重构方案评估

评估日期：2026-10-12。本文用于技术选型和实施规划，尚未开始代码重写，也未完成 Rust 原型与移动端性能验证。

## 1. 决策与目标

**已确定：使用 Rust 实现跨平台生成核心，替代客户端对 Python 运行时的依赖；新界面不再使用 Vue。**

**基础工程采用 Flutter 实现 Android、iOS、Windows、macOS、Linux 和 Web 界面。** 用户已要求按 `app/` + Rust workspace 结构建立工程。Flutter 文本编辑体验与各平台表现仍需通过原型验证；Rust 核心保持独立。

产品目标：

- 手机和桌面安装后即可使用，字体随包提供，基本生成与导出完全离线运行。
- 客户端直接调用 Rust 原生库，不要求用户安装 Python 或手动启动本地服务。
- Web 支持用户手动启动一个服务程序，该程序同时提供页面和 API。
- 移动端与桌面共享生成规则，分别适配触控、键盘、文件选择和导出体验。
- 保留当前手写参数、字体上传、背景图、文本导入、插图、预览与图片/PDF 导出能力。

“全平台”指目标平台均有完整运行路径，不代表第一阶段就支持每种 CPU 架构，也不代表一套页面布局适用于所有设备。最低系统版本、首批架构和发布渠道需要在平台原型验证后确定。

## 2. 总体结论与取舍

Rust 能合理实现当前业务。推荐组合是：**现有库负责字体、图片和文件格式，自行移植手写算法与业务规则。** 不复刻完整 Pillow、OpenCV、Word 或 PDF 引擎。

选择 Rust 的主要理由是独立核心可同时用于原生客户端和服务端，适合像素处理，并能减少应用代码中的内存安全问题。Rust 并非所有维度都优于 C++：C++ 的图形生态更完整；Dart 的 Flutter 集成更简单。既然已选 Rust，应通过控制依赖和验证效果兑现收益，而非预设安装包必然很小、生成速度必然大幅提升。

| 项目 | 评估 | 依据或限制 |
| --- | --- | --- |
| 跨平台生成核心 | 可行 | 排版、连通区域和像素扰动算法可移植 |
| Android/iOS 离线生成 | 架构可行，待真机验证 | 原生库集成、内存、取消任务和系统生命周期需验证 |
| 桌面与 Web 共用引擎 | 可行 | 原生桥接与 HTTP 服务调用相同核心 |
| 与 Python 输出逐像素一致 | 不作为默认承诺 | 字体栅格化、随机数、舍入和编码器可能不同 |
| 保持用户可感知的效果与功能 | 主要验收目标 | 需要固定样本、规则测试和人工效果评审 |
| 完全使用纯 Rust 库 | 优先方向，不作硬约束 | 字体或图像能力不足时可使用必要的 C/C++ 库 |
| 包体与性能改善 | 待测量 | 字体、缓冲区和原生依赖仍可能占主要成本 |

## 3. 架构与运行方式

```text
Flutter 客户端：Android / iOS / Windows / macOS / Linux
                         │
                 flutter_rust_bridge
                         │
                         ▼
                  Rust 生成核心
                         ▲
                         │
浏览器 → Flutter Web → Rust HTTP 服务
                       ├── 托管 Web 静态页面
                       ├── 管理任务和输出文件
                       └── 调用同一个生成核心
```

### 3.1 原生客户端

Flutter 通过 FFI（外部函数接口）调用 Rust。Android 打包原生共享库，iOS 将原生库链接进应用；桌面按平台打包所需原生库。客户端不运行 FastAPI，也不启动监听端口的后台服务。

生成任务在后台执行，进度通过事件传回界面。文件选择、系统分享、用户目录和导出授权由客户端适配层处理。界面向核心传入字体数据、输入资源与显式输出位置，核心不依赖全局工作目录。

### 3.2 Web 与自托管

用户启动一个 Rust 服务程序后，浏览器访问该服务提供的页面。前端与 `/api` 保持同源，避免公网 HTTPS 页面访问用户本机 HTTP 服务的复杂限制。服务程序包含或随包提供 Web 静态资源和默认字体。

建议默认绑定 `127.0.0.1`。局域网和公网访问采用明确配置，并配套鉴权、上传与资源限制。手机连接电脑时使用电脑的网络地址，不能使用手机自身的 `127.0.0.1`。

部署到服务器时，提供容器镜像与 HTTPS 反向代理部署说明。开发者工具链与普通用户启动方式分开：用户不需要安装 Flutter、Rust 或 Python。

浏览器内使用 WebAssembly 运行核心可作为后续研究项。当前目标允许手动启动后端，第一阶段不为 WASM 增加线程、内存和文件系统适配工作。

### 3.3 推荐的代码边界

以下为拟议目录，实施时再创建：

```text
crates/
  handwriting-core/     # 参数、排版、字体、渲染、图片处理和导出
  handwriting-bridge/   # Flutter 原生调用、任务句柄和进度事件
  handwriting-server/   # HTTP、WebSocket、持久化与静态页面
app/                    # Flutter 应用与平台适配
```

先保持这几个边界，不按每种算法拆 crate。核心不依赖 Flutter、HTTP、SQLite 或系统 UI；桥接层和服务层共享任务语义，各自管理生命周期与存储。

## 4. 当前业务与候选库

下表是候选组合，不是已验证的依赖清单。版本在原型阶段结合 Rust 工具链、目标平台和许可证锁定，应用提交 `Cargo.lock`，不使用浮动版本作为发布依据。

| 当前实现或业务 | Rust 方案 | 迁移方式与重点 |
| --- | --- | --- |
| handrightbeta 排版和扰动 | 自行移植，使用 `rand` / `rand_distr` | 保留参数含义、分页与连通区域扰动 |
| Pillow 字体绘制 | 优先验证 `fontdue`；备选 FreeType Rust binding | 验证现有字体、字体度量、基线和上传字体 |
| fontTools 字符覆盖检测 | `ttf-parser`；复杂字体可评估 `read-fonts` / `skrifa` | 主字体与备用字体选择由核心实现 |
| 复杂文字 shaping | `harfrust` | 按目标文字范围引入，不能替代手写排版 |
| 图片读写、缩放和合成 | `image` | 明确色彩、透明度、格式与解码限制 |
| 图像滤波、形态学和几何变换 | `imageproc` + 自定义算法 | 验证与 OpenCV 的数值和边界差异 |
| HoughLinesP 与图片识别 | 自定义检测；必要时使用 OpenCV Rust binding | 标准 Hough 直线不能直接代替概率 Hough 线段 |
| 一维 DBSCAN | 小型专用实现 | 保留核心点、边界点与噪声语义 |
| DOCX 导入 | `zip` + `quick-xml` | 按当前文本、表格和 OMML 文本提取需求实现 |
| 图片 PDF | `pdf-writer` | 每页嵌入 JPEG，无须完整 MuPDF |
| 多页图片 ZIP | `zip` | 明确顺序、命名和压缩策略 |
| FastAPI 与 WebSocket | `axum` + `tokio` + `serde` | 显式参数校验，保留必要的 API 兼容 |
| SQLite 任务记录 | `rusqlite`，按需使用 bundled SQLite | 结果存文件，数据库只保存元数据 |
| Flutter 原生集成 | `flutter_rust_bridge` | 验证构建、线程、事件与大数据传递 |
| 日志与错误 | `tracing` + `thiserror` | 核心返回结构化错误，界面负责中英文文案 |

`imageproc` 不承诺覆盖 OpenCV 全部能力。`fontdue` 不处理 shaping，其默认布局也不承担本项目的排版规则。shaping 若采用 `harfrust` 与 `read-fonts`，应评估是否能减少重复字体解析，而非同时堆叠多套字体库。

`skia-safe` 是备选图形方案，已有移动端构建目标，但会增加原生构建和依赖成本。不能假设 Rust 能复用 Flutter 内部的 Skia 实例。

## 5. 手写引擎迁移

### 5.1 复刻现有算法的关键

当前安装的 handrightbeta 8.7.0 先排版并绘制二值前景图，再通过四邻域连通搜索提取像素区域，对区域施加位移、旋转和墨色变化，最后合成背景。

源码中的 stroke 是连通像素区域，不是字库内的真实书写轨迹。相连的笔画甚至字符可能属于同一区域。仅逐字旋转无法保持当前效果，也不需要引入机器学习模型。

迁移应覆盖：

- 流式与网格排版、边距、字间距、行间距和字号扰动。
- 标点禁则、手动分页、右对齐和英文空格处理。
- 删除线、错误字符模拟和墨色变化。
- 二值蒙版、连通区域、旋转方向、角度单位和像素舍入。
- 背景合成、插图位置与单页预览提前结束。

使用当前测试和样张提取行为契约，避免逐行翻译 Python 的实现细节。第一阶段保留参数语义，效果改进在有对照结果后独立进行。

### 5.2 字体、数学符号与插图

`backend/symbol_fallback.py` 包含备用字形、竖式分数、根式、根指数和横线绘制，均需纳入迁移。普通字体 shaping 库不会自动实现这些应用规则。

建议内部使用文本、分数、根式、插图和分页等有限节点表示；保留对现有输入标记的解析。动态私用区字符与 monkey patch 不再作为核心机制。范围以现有功能为限，不扩展成完整 LaTeX 或 Word 排版系统。

缺字回退必须在测量和绘制阶段使用同一字体。默认字体与备用字体随包提供，不以某个平台的系统字体作为一致性前提。复杂文字按 shaping cluster 而非任意 Unicode 字符施加扰动，避免破坏组合字形。

### 5.3 随机数与效果一致性

Rust 与 Python 使用同一 seed 不会自然生成相同结果。当前实现还混用了局部随机对象、全局随机状态和 NumPy 随机数，不能将旧 seed 视为完整复现契约。

新核心显式接收 seed，固定 PRNG、采样顺序和算法版本；同一构建内结果应可重复。跨平台是否达到逐像素一致，需要额外验证浮点、字体和编码器差异。

验收分两层：关闭扰动时验证排版和边界；开启扰动时验证分布、可重复性和视觉效果。JPEG 质量值相同也不意味着编码结果或体积相同。

## 6. 图像分析与文件处理

### 6.1 图片识别与仿手绘滤镜

仿手绘滤镜包含高斯自适应阈值、低频随机位移场、重采样、透明度扰动和墨滴噪声。基础操作优先复用库，有限的采样与合成规则自行实现。需要核对颜色通道、阈值边界、插值和越界处理。

图片识别应同时验证干净合成图与真实纸张、倾斜和噪声样本。`imageproc` 的 Hough 接口返回极坐标直线，当前算法依赖线段端点来计算边距，不能直接替换。

`backend/tests/test_identify.py` 记录了已知问题：行距可能实际返回笔画厚度，以及无可检测线条时的降级行为不完善。重写目标应返回真实行距；无法可靠识别时返回明确状态，让用户手动设置，不能把这些缺陷固化成兼容要求。

如果纯 Rust 路线无法达到识别要求，可通过 Rust binding 使用 OpenCV 原生库，裁剪所需模块。此时必须评估 Android/iOS 构建与包体成本，不能将其等同于纯 Rust 依赖。

### 6.2 DOCX、PDF 与 ZIP

当前 DOCX 提取读取文本节点、换行、制表符、表格及 OMML 文本，并不还原完整 Word 版式或公式语义。使用 ZIP/XML 库实现对应提取规则足够；处理 namespace 与合并单元格，并明确正文和表格的顺序规则。

当前 PDF 导出将每页压为 JPEG 后嵌入页面，`pdf-writer` 的图片示例覆盖该路径。优先逐页编码并释放像素缓冲。PDF 写入器仍可能保留编码数据，需测量长文档峰值，不能仅凭逐页渲染宣称恒定内存。

当前 PDF 页面宽高直接使用图片像素作为 point。新实现应显式区分像素、DPI 和物理纸张尺寸；默认纸张行为在迁移验收时确认，不能无声改变。

图片格式应先列出现有接受范围。PNG/JPEG 是基本路径，其他格式依据实际需求启用；扩展名或容器相同不代表新旧解码器兼容性完全相同。

## 7. 任务、内存与安全边界

### 7.1 任务生命周期

桥接层和服务层采用一致的 pending、processing、completed、failed 状态语义，并新增明确的取消行为。核心提供协作取消检查点；取消异步句柄不会自动终止已经运行的 CPU 任务。

客户端默认先验证单个生成任务并发。服务端可从现有最多 2 个执行任务开始，结合内存测试调整。CPU 密集生成使用受控工作线程或 `spawn_blocking`，不占用异步请求线程，也不盲目按所有 CPU 核心并行生成整页。

手机长任务受到系统挂起和后台限制。首版不承诺退出或后台后仍持续生成；挂起、终止和恢复时应保留输入与明确任务状态，避免假进度和损坏文件。

服务端任务状态、结果文件、过期清理和 WebSocket 推送分别管理。第一阶段保留 30 分钟过期语义，并明确清理不能删除正在写入或下载的结果。SQLite 持久化元数据不等于任务可在崩溃后继续计算，重启后需明确标记中断任务。

### 7.2 内存与数据传递

2480 × 3508 的 RGBA 页面约占 33 MiB，多份背景、蒙版、位移场和输出缓冲会叠加。字体也可能较大。优先逐页处理、复用缓冲、限制输入尺寸与缓存容量。

预览可以返回压缩图片字节；大文件导出通过应用私有目录或资源句柄传递，交给客户端执行系统保存与分享。避免用 Base64 或频繁 FFI 拷贝传输整页像素，进度事件不携带完整图片。

### 7.3 文件与网络边界

- 核心校验参数、图片尺寸、解码资源和布局有效性，错误使用稳定代码表示。
- Web 服务限制请求体、解压后大小、任务数量和结果访问，不能依赖 Rust 自动防止资源耗尽。
- 原生客户端数据写入平台可写目录，不写安装目录，也不依赖进程级 `chdir`。
- Web 本地服务保留 Origin/Referer 与 CORS 边界；局域网或公网模式另设鉴权。
- 核心不包含遥测。客户端与服务端分别决定 Sentry 等集成，延续桌面版默认关闭上报的行为。

## 8. 界面与平台体验

Flutter 是推荐方案，但需要先验证中文输入法、长文本选区、复制粘贴、撤销、插图输入和 Web 文本编辑体验。当前 Markdown、KaTeX、书信格式化与插图工具是 JavaScript 逻辑；选择 Flutter 后不能假设可直接复用，需要按职责移植到 Dart 或 Rust，并沿用原有测试样例。

| 平台 | 主要适配 |
| --- | --- |
| Android/iOS | 分步参数设置、触控预览、软键盘、系统文件选择和分享 |
| 桌面 | 参数与预览并排、快捷键、拖放、窗口缩放和文件导出 |
| Web | 浏览器下载、连接状态、窄屏、键盘与文本输入 |

界面复用当前设计语言，默认中文并提供英文翻译。错误文案由界面根据结构化错误生成，Rust 核心不拼接 UI 文案。

全平台原型验证后再冻结最低系统版本与架构矩阵。macOS/iOS 使用对应 Apple 构建环境，Android 使用 NDK，Windows/Linux 各自验证安装、启动和导出。CI 需要真实打包验证；不能把文档宣称的平台支持视为本项目已通过测试。

Apple 签名、公证和发布凭据作为发布阶段的独立依赖。macOS 未签名分发的 Gatekeeper 行为仍需说明；Rust 重写不会自动消除这些安装限制。

## 9. 兼容与渐进迁移

Python/Vue/Electron 版本在新实现通过验收前继续可用。新旧实现并行开发，避免先删除旧系统再补齐功能。

建议 Rust 服务初期保留当前生成、任务状态、结果、字体、版本和上传接口。接口适配层负责将现有字符串表单转换成核心的数字、布尔和枚举参数，核心不延续全字符串模型。

现有字体资产、用户预设与输入标记需要迁移规则。SQLite 是否复用由 schema 审计决定；临时任务可以过期，但用户输入和预设不能随之丢失。

必要时使用 `PyO3` 让 Python 调用局部 Rust 实现，以便逐步对照。这只是可选验证工具，不是最终客户端依赖。发版继续使用 semantic-release，并在实现新打包方式后更新版本同步与产物上传流程；不手改当前版本文件。

## 10. 实施阶段与验收

| 阶段 | 交付内容 | 验收标准 |
| --- | --- | --- |
| 0：行为基线 | 功能清单、固定字体和样张、参数与输出规则 | 每项现有功能均有验收依据，已知缺陷单独列出 |
| 1：Rust 渲染原型 | 中文/英文排版、二值图、连通区域扰动、图片输出 | 主要字体可加载；分页、标点和扰动效果达到基线；固定 seed 可重复 |
| 2：原生平台原型 | Flutter 桥接、进度、取消、离线预览和导出 | Android/iOS 真机及桌面验证，无 UI 阻塞，资源释放和生命周期正确 |
| 3：功能补齐 | 数学符号、插图滤镜、背景识别、DOCX、PDF、ZIP | 现有测试场景迁移通过，识别缺陷得到修正，导出尺寸与质量符合约定 |
| 4：Web 服务 | API、队列、SQLite、静态页面与分发程序 | 单程序启动可用；上传、查询、断线、过期与重启行为验证通过 |
| 5：界面与发布 | 自适应界面、中英文、用户数据迁移、CI 安装包 | 平台功能矩阵通过，安装后无需开发工具，生成与导出全链路可用 |

阶段 1 与阶段 2 是继续大规模迁移的前置条件。遇到字体或性能问题时调整局部库选型，不把所有验证推迟到界面完成之后。

性能指标在固定设备、页面尺寸、字体、文本和滤镜参数下测量：冷启动、首张预览、单页/多页导出时间、峰值内存、包体和取消延迟。先取得 Python 与 Rust 基线，再确定可接受预算，不提前承诺提升倍数。

测试优先迁移现有 typography、text layout、symbol fallback、inline images、handdrawn filter、DOCX、PDF 和并发场景。像素对照用于稳定场景；字体边界、随机滤镜和有损编码采用明确容差与人工样张评审。Flutter 测试采用对应测试工具，Web API 与浏览器行为仍可使用现有测试资产；Electron 专用测试不能原样用于 Flutter。

## 11. 主要风险与待确认项

| 风险或决策 | 处理方式 |
| --- | --- |
| 原生桥接尚未接入 | 当前 bridge 仅提供 Rust API 边界；后续生成 FFI 绑定并验证原生构建 |
| 字体与现有度量差异 | 原型先测全部默认字体和代表性上传字体，必要时选择 FreeType |
| 图像算法无法等价替换 | 真实样本对照，明确容差；必要时引入裁剪后的 OpenCV |
| 移动端内存和后台限制 | 真机优先、逐页处理、协作取消，定义挂起与恢复行为 |
| Flutter 文本编辑体验不达标 | 在完整界面迁移前验证输入、选区、插图和 Web 编辑 |
| 默认字体分发权限 | 分别审计字体许可证，不能由引擎许可证推导 |
| 手写算法源码移植许可 | 当前包内 BSD-3-Clause 要求保留版权、条款和免责声明；审计其余源码来源 |
| 平台与架构覆盖成本 | 原型后冻结首批矩阵，再安排构建与发布预算 |
| 效果兼容与质量改进冲突 | 第一阶段以功能和效果基线为准，变化单独记录并验收 |

当前不估算总工期：字体、图片识别、移动端性能和 UI 选择仍有实质不确定性。完成阶段 1、2 后，按模块拆分工作量与发布范围。

- [flutter_rust_bridge 平台说明](https://cjycode.com/flutter_rust_bridge/guides/cross-platform/overview)：原生平台与 Web 支持。
- [rust-skia 平台与构建说明](https://github.com/rust-skia/rust-skia)：Skia binding 的平台目标及原生构建成本。
