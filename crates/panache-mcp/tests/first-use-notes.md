# 从「帮我做一份手写作业」到拿到文件

这次沿着学生可能经历的顺序检查 Panache。问题有两个：第一次用的人能不能知道该给什么材料？导出成功以后，聊天客户端能不能真的拿到选中的那一版？

## 先试已有功能

在 main 的 `f8d703cbecdae8ae3eb44f8c9bc66a2a6254178b` 上，用 Python MCP SDK 通过标准输入输出启动服务，读首次握手的说明，查工具，再实际写稿。桌面版早已有「应用设置 → 连接 AI 客户端」入口；这一步要在服务能说话之前完成。原来的握手能指导看图、用照片、调整笔迹和导出。我们用同一段合成文字实际生成了打印 PDF、原纸成品和透明字迹，三个都能打开。

卡住的是文件怎么从运行 Panache 的电脑到聊天里。原工具报告文件路径、版号和页数，客户端在同一台电脑上可以使用。我们让测试客户端只用工具回复做附件，它拿到了三个路径，却拿不到三份文件的内容。

## 沿途改了什么

1. 在连接前就能读到的 README 补上三种用途。连接后，先用已有文字或照片，只有用途不清时才举与材料有关的例子。照片需要由客户端传给 Panache；另一台电脑上的路径不能把照片传过来。
2. 让首次说明把「字号」说成「字大一点」，把「降低墨迹浓度」说成「墨色淡一点」。用普通图看小样，收到反馈后再看新版。保存并使用用户选中的版号，即使后来又改了一版。
3. 导出增加可选的 `include_file`。客户端提出请求时，512 KiB 以内的 PDF 或 ZIP 可作为 MCP 内嵌资源随回复传送，也就是直接带上文件内容。读取的是刚生成的文件句柄，避免按路径重新打开时读到别的文件。既有调用仍可只取路径。上限按原文件计算，用来限制一次回复的体积。
4. 把「生成」和「交付」分开。客户端收到内容后，还要把它显示为可打开的附件。遇到过大的文件或传送失败，保留已生成的文件，说明应从哪台电脑取回。服务端看不到用户的聊天界面，不能据此确认用户已经打开。

## 先核对要问什么

下面是作者写的固定对话示例。把再次索要用户已经给出的文字、照片或用途算为一次多问。一条消息可同时收齐材料和用途。

| 已有材料和意图 | 向导示例 | 追问轮数 | 多问 |
| --- | --- | ---: | ---: |
| 只有「帮我做一份手写作业」 | 「把要写的内容贴给我。你想打印、填在自己的练习纸上，还是只留能贴到别处的字？」 | 1 | 0 |
| 已给正文，明确要打印 | 「我用这段话做打印版。」 | 0 | 0 |
| 已给正文和练习纸照片，也说明要填在照片上 | 直接用客户端能传给服务的照片；传不了就说明限制。 | 0 | 0 |
| 已给正文，明确要透明字迹 | 直接做透明稿，说明解开 ZIP 可拿到 PNG。 | 0 | 0 |

负对照是对第二行再问「想打印还是只要字迹？」。按同一规则计一次多问。四行示例合计一次必要追问、零次多问；这是示例的话术预算。真实模型的追问次数、学生理解程度和找到附件所需的时间均未测。另一个可复核的代理指标是检查握手中是否出现五项具体表达：三种成品、合并索取缺失正文、明确请求跳过选择、用日常用语提改动、沿用选中的版本。`compare_first_use.py` 检查的是原文片段，不能判断所有同义表述或读者理解。

## 用真实服务复走

Python 固定安排用户事件，Rust 服务真实建稿、排版、调参和导出。测试客户端把内嵌数据写入自己的收件目录。另一个检查步骤才读取服务器成品，比较两端内容。两者在同一测试机上，隔离的是客户端取文件的方法。没有运行聊天模型或招募学生。

| 在同一份材料上做的事 | 观察结果 |
| --- | --- |
| 打印稿先看第 1 版，按「字大一点」改成第 2 版，选中第 2 版后再创建第 3 版 | 从客户端取回的第 2 版 PDF 为 32,704 字节。解出 PDF 页图，与第 2 版小样的 RGB 像素完全相同；第 1 版的平均通道误差约 1.786（0–255）。 |
| 用合成练习纸做第 1 版；另测服务器还没有收到照片 | 成品保留纸面 200,000 个像素中的 196,992 个，其余是文字区域。ZIP 中的页图与小样逐像素相同。缺图的真实请求被拒，12 张表均无变化。 |
| 直接做透明稿 | 第 2 版 ZIP 中的 PNG 同时含全透明和不透明像素；全页与预览一致。另一个合法 ZIP 不能冒充这份文件。 |
| 不共用路径，只按工具回执收文件 | 基线与候选生成的三份目标文件及一个旧版对照均逐字节相同。测试客户端能打开且与参考成品匹配的文件，从 0/3 到 3/3。这个数字衡量文件能否传到客户端。 |
| 只要路径，或请求随回复传送 1,639,341 字节的大文件 | 前者保持原回执结构，后者报告 `too_large`；两次均保留有效导出，没有附上截短的文件。另有 Rust 测试核对 524,288 与 524,289 字节的分界。 |

所有普通预览前后都核过 SQLite 全表内容；导出只新增对应的成品记录，没有新增检查单。桌面配置界面、特定第三方客户端的附件按钮、无法显示图片时的真人判断，均未在此实验覆盖。量化结果不是耗时、转化率或用户满意度。

## 怎样复跑

需要项目指定的 Rust、官方 Markdown worker、仓库字体、Python 的 MCP SDK 和 Pillow，以及 Poppler 的 `pdfimages`。从候选源码运行以下脚本；两个输出目录须尚未存在。`BASE_BIN` 是从上面的 main 单独构建的程序，`NEW_BIN` 是候选程序，`WORKER` 指向随桌面版提供或由项目脚本构建的 `prepare-text-worker.js`。

```sh
cargo build --locked --release -p panache-mcp
T=crates/panache-mcp/tests
python "$T/first_use.py" "$BASE_BIN" "$WORKER" --baseline --out main-run
python "$T/first_use.py" "$NEW_BIN" "$WORKER" --out candidate-run
python "$T/compare_first_use.py" main-run candidate-run
cargo test --locked -p panache-mcp
```

每次会新建隔离库。报告保存握手说明、真实导出参数、版号、文件摘要、小样和客户端收到的文件。稿件 ID 每次重新生成，核对的是相同输入、版号和文件内容。
